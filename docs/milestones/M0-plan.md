# M0 — Foundations · PLAN

- **Status:** PLAN (awaiting review). **Blocked by:** ADR 0001 approval (Gate 2). Gate 1
  (YouTube legal) does **not** block M0 — no data collection happens here.
- **Goal (from Part 6):** a repo skeleton a junior dev can clone and run in one command,
  with lint/format/hooks, an offline test harness, structured logging, env-based config,
  Docker Compose for local dev, and green CI.
- **Definition of done (from the spec):** `make test` runs green from a clean clone with
  **one command**, and CI is green. No application/business logic yet — foundations only.

## Scope — what M0 IS and IS NOT

**IS:** project scaffolding, tooling, config plumbing, logging, the test harness itself,
the RISK-register generator script (it must exist from the start so it can run "at the end
of every milestone"), the documentation skeletons, Docker Compose, CI.

**IS NOT:** no `price_observation` schema (that is M1), no connectors (M2+), no models
(M4). No YouTube-shaped anything (Gate 1). Per Part 1.2 I will not pre-scaffold later
milestones — only the empty package structure and the cross-cutting tooling live here.

## Files I plan to create

**Project root**
- `pyproject.toml` — project metadata, dependencies, ruff config, pytest config; managed by `uv`.
- `uv.lock` — pinned lockfile (reproducible installs).
- `Makefile` — the one-command surface: `make setup`, `make test`, `make lint`, `make fmt`, `make up`, `make down`, `make risks`.
- `.pre-commit-config.yaml` — ruff lint + ruff format + trailing-whitespace/EOF hooks.
- `.env.example` — every config key with placeholder values; real `.env` is git-ignored.
- `docker-compose.yml` — `app` + `postgres:16` services for local dev (Postgres present now so M1 can use it immediately; M0 tests do **not** require it).
- `Dockerfile` — slim Python 3.12 image for the app/CLI.
- `README.md` — plain-language "what this is / how to run it" for a non-technical founder + a junior dev.
- `.gitignore` — already created.

**Application package (empty but importable — no business logic)**
- `src/vervana/__init__.py`
- `src/vervana/config.py` — `pydantic-settings` Settings loaded from env (DB URL, API keys as `Optional`, timezone pinned to `Asia/Kolkata`, log level). Nothing secret has a real default.
- `src/vervana/logging.py` — `structlog` JSON logging setup + a `get_logger` helper.
- `src/vervana/cli.py` — a `Typer` app with a single `version` / `healthcheck` command to prove the entrypoint and config load work. Connector/ingest commands come later.
- `src/vervana/time.py` — IST/UTC helpers enforcing "store UTC, display IST, no naive datetimes" (Part 7). Small, but foundational and worth testing early.
- `src/vervana/money.py` — integer-paise helpers (parse/format ₹, never float) (Part 7). Same rationale.

**Tests (offline, no network — Part 1.5)**
- `tests/test_config.py` — Settings loads from a fake env; secrets absent → fields are `None`, not crashes.
- `tests/test_time.py` — naive datetime is rejected; UTC↔IST round-trips; IST display correct.
- `tests/test_money.py` — rupee/paise round-trip; no float ever appears; parsing "₹45.50" → 4550 paise.
- `tests/test_smoke.py` — package imports; `cli healthcheck` exits 0.

**Tooling / scripts**
- `scripts/gen_risk_register.py` — greps the codebase for `RISK[<ID>]:` blocks and regenerates `docs/RISK_REGISTER.md` from them (Part 2: the register is generated, never hand-edited). In M0 the code has **zero** `RISK[` tags yet, so the generated register must correctly render an **empty** table plus the 12 seed rows from the spec marked "not yet reached in code." I will design it so the *seed* R1–R12 definitions live in a data file the script reads, and the *code-tag* section is pure grep output — the two are shown side by side so drift is visible.
- Wire `make risks` → this script.

**Documentation skeletons (created now, filled as milestones land — Part 8)**
- `docs/RISK_REGISTER.md` — generated by the script (not hand-edited).
- `docs/RUNNING_COSTS.md` — seeded from the ADR cost table + the "variable/observer costs are separate" split.
- `docs/OPEN_QUESTIONS.md` — seeded with the three known-unknowns: eNAM API access (§4.4), GODL-India clause text (§4.1), GST treatment of a data subscription (Part 8); plus the WhatsApp/ASR residency caveat from the ADR.
- `docs/DATA_DICTIONARY.md` — skeleton with the "meaning / source / must-never-be-used-for" column headers; tables filled in M1.
- `docs/RUNBOOK.md` — skeleton with the three scenarios named (ingest fails, key expires, parser flags everything) + VPS restore-from-backup; filled as the relevant systems exist.

**CI**
- `.github/workflows/ci.yml` — on push/PR: `uv sync`, `ruff check`, `ruff format --check`, `pytest` (offline), and an Alembic-config sanity check placeholder (real migrations arrive in M1). Must be green.

## Tests that will prove M0 works (shown as real output at done-time)

1. `make test` from a **fresh clone** → all tests pass, **no network** (proven by running with networking disabled / no external hosts touched).
2. `make lint` and `make fmt --check` → clean.
3. `make risks` → regenerates `docs/RISK_REGISTER.md`; committing and re-running produces **no diff** (proves generator is deterministic and register isn't hand-edited).
4. `cli healthcheck` → exits 0, logs a structured JSON line, confirms timezone = Asia/Kolkata.
5. CI green on GitHub Actions.
6. `docker compose up` brings up app + postgres locally (shown, but **not** required by `make test`).

## Open questions for this milestone

1. **ADR approval (blocking).** M0 cannot start until ADR 0001 is approved or amended.
   If the founder changes the stack, this plan changes with it.
2. **`uv` vs `pip-tools`/`poetry`.** I've chosen `uv` for speed and reproducibility; if the
   junior dev's environment or the founder prefers plain `pip`+`requirements.txt`, say so —
   it's a one-line change to the plan.
3. **CI host.** I've assumed **GitHub Actions** (free for this size, and the repo will live
   on GitHub given the co-authored-commit convention). If the code will live elsewhere
   (GitLab/self-hosted), tell me and I'll swap the workflow.
4. **RISK register shape.** I intend the generated register to show two synchronized
   sections — the 12 seed definitions (from a checked-in data file) and the live code-tag
   occurrences (pure grep) — so drift between "risks we said we'd tag" and "risks actually
   tagged in code" is visible at a glance. Confirm that's the shape you want, or say if you'd
   rather the register be *only* the code-tag grep with the seed list living elsewhere.
